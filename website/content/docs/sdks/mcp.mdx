title: MCP Server
description: Expose a bigRAG instance over the Model Context Protocol so Claude Desktop, Cursor, and other MCP clients can retrieve from your collections natively.

bigRAG ships an [MCP](https://modelcontextprotocol.io) server in two
shapes:

- **Remote HTTP** — mounted on the bigRAG API at `/mcp`, works with
  Claude's custom connector, remote Cursor, and any streamable-http
  client. No local install.
- **Local stdio** — the `bigrag-mcp` CLI, for Claude Desktop's
  `config.json` and older Cursor setups.

Both share the same toolset. Scope (all-collections vs pinned to one
collection) is derived from the API key.

## Studio manages its own credentials

Studio's **MCP** page (`/mcp`) is the canonical way to set one up.
Creating an MCP there:

1. mints a fresh bigRAG API key dedicated to that MCP (not shared
   with `/api-keys`);
2. shows the full URL (with token embedded) exactly once — copy it
   straight into Claude's custom connector or Claude Desktop config;
3. persists the MCP as a first-class server-side resource (title,
   server name, collection scope, key prefix) that you can later
   rotate or delete.

You do **not** pick from existing keys on `/api-keys` — MCP credentials
live in their own namespace. If a URL leaks or is lost, click **Rotate
key** on the MCP's detail dialog. The previous token stops working
immediately on the next request.

## Scoping to a single collection

When creating the MCP in Studio, set **Collection scope** to pin it to
one collection. The bigRAG API blocks cross-collection endpoints for
scoped MCPs with a 403, and both transports adjust their toolset:

| MCP scope | Tools exposed |
|-----------|---------------|
| **All collections** | 8 tools including `list_collections` and `multi_collection_query`. |
| **Pinned to `X`** | 6 tools, all with `collection` pre-bound to `X`. `list_collections` and `multi_collection_query` are hidden. |

There is no separate `BIGRAG_COLLECTION` env var — the key itself
carries its scope. To change scope, delete the MCP and create a new
one (or rotate after editing via the REST API).

## Remote HTTP (Claude custom connector, remote Cursor)

No local install. Studio hands you the full URL at MCP creation time;
its shape is:

```
https://bigrag.example.com/mcp?token=bigrag_sk_...
```

For Claude's custom connector beta:

- **Name**: anything you like, e.g. "bigRAG" or "bigRAG runbooks".
- **Remote MCP server URL**: paste the URL above.
- **OAuth Client ID / Secret**: leave blank — bigRAG authenticates via
  the `?token=` query param, not OAuth.

The token appears in the URL. Treat the URL like a password: it may
end up in reverse-proxy and server logs. If a URL leaks, revoke the
key in Studio.

Under the hood the endpoint is a FastMCP server with
`stateless_http=True` and `json_response=True`; every request carries
the token and is dispatched through the bigRAG REST API, so all
auth / scope / rate-limit rules apply uniformly.

## Local stdio (Claude Desktop, legacy Cursor)

Install the CLI:

```bash
uv tool install bigrag
# or: pip install bigrag
```

Run directly:

```bash
BIGRAG_URL=https://bigrag.example.com \
BIGRAG_API_KEY=bigrag_sk_... \
bigrag-mcp
```

Flags:

| Flag | Default | Notes |
|------|---------|-------|
| `--base-url` | `http://localhost:4000` | also read from `BIGRAG_URL` |
| `--api-key` | _(none)_ | also read from `BIGRAG_API_KEY` |
| `--transport` | `stdio` | alt: `streamable-http` |
| `--port` | `6101` | for streamable-http only |

Scope is discovered on startup via `GET /v1/auth/whoami`. If the key
is pinned to a collection, the CLI registers the scoped toolset
automatically.

### Claude Desktop config

Add to `~/Library/Application Support/Claude/claude_desktop_config.json`
(macOS) or `%APPDATA%\Claude\claude_desktop_config.json` (Windows):

```json
{
  "mcpServers": {
    "bigrag": {
      "command": "bigrag-mcp",
      "env": {
        "BIGRAG_URL": "https://bigrag.example.com",
        "BIGRAG_API_KEY": "bigrag_sk_..."
      }
    }
  }
}
```

Restart Claude Desktop. The server appears under the tools icon with
the tools registered for that key's scope.

## Tools

All tools are thin wrappers around `/v1/*` endpoints. They honor the
same auth, scopes, and rate limits as any other API client.

### Full-workspace key

| Tool | Calls | Purpose |
|------|-------|---------|
| `list_collections` | `GET /v1/collections` | Discover what's available. |
| `get_collection` | `GET /v1/collections/{name}` | Embedding / chunking config. |
| `get_collection_stats` | `GET /v1/collections/{name}/stats` | Document/chunk/token counts. |
| `query` | `POST /v1/collections/{name}/query` | **Main tool** — top-k chunks for a question. |
| `multi_collection_query` | `POST /v1/query` | Search several collections in parallel. |
| `list_documents` | `GET /v1/collections/{name}/documents` | Paginate documents. |
| `get_document` | `GET /v1/collections/{name}/documents/{id}` | Metadata for one document. |
| `get_document_chunks` | `GET /v1/collections/{name}/documents/{id}/chunks` | All chunks of a document. |

### Collection-pinned key

Same six tools minus `list_collections` and `multi_collection_query`,
and with the `collection` / `name` argument removed (pre-bound from
the key's scope).

## Example interaction

Once configured:

> **User:** What does our runbook say about Postgres failover?
>
> **Model:** _(invokes `query` with `collection: runbooks`,_
> _`query: "Postgres failover procedure"`, `top_k: 5`)_
>
> _(receives top-5 chunks; synthesises an answer citing `document_id`s)_

## Limitations

- Ingestion (upload, S3 jobs, webhooks) is intentionally not exposed —
  MCP tools target retrieval workflows. Use the HTTP API, a language
  SDK, or the Studio UI for writes.
- Streaming SSE endpoints (document progress, collection events) are
  not wrapped — MCP tools are request/response only.
- OAuth 2.0 flows are not implemented. For URL-based clients, use the
  token-in-URL pattern above. OAuth is tracked as a future addition.
