The admin UI is the Vite + TanStack Router single-page app packaged with bigRAG. Every control is also a REST API, so the admin UI is optional — you can run bigRAG headless — but it's the fastest way to bootstrap, prototype, and operate the platform.

## Running the Admin UI

```bash
pnpm dev:app        # admin UI on http://localhost:3000
```

The admin UI calls the FastAPI backend directly. The default API URL is `http://localhost:4000`; override it with `VITE_BIGRAG_URL` at build/dev time or `BIGRAG_URL` in the app container. The backend must include the app origin in `BIGRAG_CORS_ORIGINS`, for example `["http://localhost:3000"]` in local development.

For cross-site production deployments, set `BIGRAG_SESSION_COOKIE_SECURE=true` and usually `BIGRAG_SESSION_COOKIE_SAMESITE=none`. Same-site subdomain deployments can usually keep `SameSite=lax`.

## Route map

| Path | Purpose |
|------|---------|
| `/setup` | One-time page to create the first admin account. Disappears once `needs_setup: false`. |
| `/login` | Email + password login for admins and members. |
| `/overview` | Platform-wide stats — collection count, document states, queue depth, readiness. |
| `/collections` | List, create, delete, and search collections. |
| `/collections/[name]` | Redirects to the collection's documents tab. |
| `/collections/[name]/documents` | Upload (drag & drop or multi-file picker), list, inspect status, and delete documents. |
| `/collections/[name]/documents/[docId]` | Document detail — chunk viewer, SSE progress, failed-ingest error, reprocess, and delete. |
| `/collections/[name]/connectors` | Redirects to the collection's connector tabs. |
| `/collections/[name]/connectors/google-drive` | Browse Google Drive, sync selected files/folders, trigger manual resync, and manage sync schedules. |
| `/collections/[name]/search` | Query tester scoped to the collection — tweak `search_mode`, `top_k`, and rerank when enabled. |
| `/collections/[name]/settings` | Edit description, metadata, metadata schema, reranking, chunking, and default query params. |
| `/chat` | Production chat UI; retrieve from one collection, stream cited answers through the backend, and continue stored conversations. |
| `/models` | Manage [embedding presets](/docs/api-reference/embedding-presets) — reusable provider + model + key tuples. |
| `/mcp` | Mint, scope, rotate, and revoke [MCP server](/docs/api-reference/mcp-servers) credentials for Claude Desktop / Cursor / custom MCP clients. |
| `/api-keys` | Mint, scope, and revoke `bigrag_sk_…` keys. Plaintext shown once at creation. |
| `/access-logs` | Access-log explorer for query, vector, chat, and evaluation traffic. |
| `/webhooks` | Register, test, and delete webhooks. Delivery history and replay are available through the API. |
| `/settings` | Tabs: Account · Server · Connectors · Usage & cost · Audit log. |
| `/evals` | Run golden-set retrieval evaluations. |

## Realtime updates

The admin UI uses session-cookie [admin realtime SSE streams](/docs/api-reference/admin-realtime) for live document progress, batch upload progress, collection stats, Google Drive sync state, access logs, audit log, usage, platform stats, and readiness. Each stream sends an immediate full `snapshot` payload that matches the related REST response, then sends later snapshots as data changes.

After batch upload, the collection documents page opens `GET /v1/admin/realtime/collections/{name}/documents/batch-status` for the returned document IDs. The panel shows completed and failed counts plus the active file, ingestion step, and latest progress message, then closes the stream when all watched documents are `ready` or `failed`.

REST document status endpoints remain available for API clients and SDKs that prefer polling. `GET /v1/collections/{name}/events` remains available for collection-wide ingestion events outside the admin UI.

## Chat specifics

The chat UI sends each turn to `POST /v1/chat`. Retrieval, prompt assembly, provider calls, citations, and conversation persistence all happen on the backend. The saved OpenAI key stays on the backend; preference responses only expose whether a key is configured. Preferences such as model, temperature, `top_k`, search mode, rerank preference, and system prompt persist via `/v1/auth/preferences`.

### Citations

Retrieved chunks carry citation provenance — `document_id`, `document_filename`, `chunk_index`, and Docling-derived `page_no` / `char_start` / `char_end` (see [`ChatSource`](/docs/api-reference/chat)). The backend hands every chunk to the LLM as `[N] (filename, page X) <text>` and instructs the model to cite with bracketed numbers. In the rendered answer, every `[N]` token is a clickable link that expands the **View sources** panel and scrolls to the matching source card; the card itself shows the document filename, chunk index, page badge, and character offsets when present.

<Callout type="info">
The admin UI uses session cookies exclusively. To automate anything the admin UI does, mint an API key at `/api-keys` and use it with one of the [SDKs](/docs/sdks/typescript) — or with raw HTTP using the same REST endpoints.
</Callout>

## When to skip the Admin UI

- **Pure backend deployment** — no admin UI process, everything via API keys and SDKs. Set `BIGRAG_ENV=prod` and use [`POST /v1/auth/setup`](/docs/api-reference/authentication) from an admin workstation to bootstrap.
- **Embedded experiences** — if you're surfacing search inside your own app, skip admin UI and build against the [query API](/docs/api-reference/query).
- **Read-only operators** — create a `member` account; they get `/overview`, `/collections` (read), and `/chat` but can't mutate.
