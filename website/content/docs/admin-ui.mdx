The admin UI is the Vite + TanStack Router single-page app packaged with bigRAG. Every control is also a REST API, so the admin UI is optional — you can run bigRAG headless — but it's the fastest way to bootstrap, prototype, and operate the platform.

The bundled interface uses normal-weight body text with slightly restrained emphasis weights so dense admin screens stay readable without feeling visually heavy.

## Running the Admin UI

```bash
pnpm dev:app        # admin UI on http://localhost:3000
```

The admin UI calls the FastAPI backend directly. The default API URL is `http://localhost:4000`; override it with `VITE_BIGRAG_URL` at build/dev time or `BIGRAG_URL` in the app container. Configure browser origins in `/settings → Security` after the API has its bootstrap database wiring.

For cross-site production deployments, enable secure session cookies and usually set `SameSite=none` in `/settings → Security`. Same-site subdomain deployments can usually keep `SameSite=lax`.

| `/settings` | Tabs: Account, Server, Security, Ingestion, Storage, Queue, Search, Chat, Webhooks, Retention, Backups, Connectors, Usage & cost, Audit log. |

## Realtime updates

The admin UI uses session-cookie [admin realtime SSE streams](/docs/api-reference/admin-realtime) for live document progress, batch upload progress, collection stats, connector sync state, access logs, audit log, usage, platform stats, and readiness. Each stream sends an immediate full `snapshot` payload that matches the related REST response, then sends later snapshots as data changes.

After a large local upload starts, the collection documents page opens `GET /v1/admin/realtime/collections/{name}/upload-sessions/{session_id}`. The panel shows received, queued, ingesting, completed, failed, and canceled counts plus a small recent item window, so 10,000-file uploads do not require a 10,000-ID status stream.

REST document status endpoints remain available for API clients and SDKs that prefer polling. `GET /v1/collections/{name}/events` remains available for collection-wide ingestion events outside the admin UI.

## Chat specifics

The chat UI sends each turn to `POST /v1/chat`. Retrieval, prompt assembly, provider calls, citations, and conversation persistence all happen on the backend. The saved OpenAI key stays on the backend; preference responses only expose whether a key is configured. Preferences such as model, temperature, `top_k`, search mode, rerank preference, and system prompt persist via `/v1/auth/preferences`.

### Citations

Retrieved chunks carry citation provenance — `document_id`, `document_filename`, `chunk_index`, and Docling-derived `page_no` / `char_start` / `char_end` (see [`ChatSource`](/docs/api-reference/chat)). The backend hands every chunk to the LLM as `[N] (filename, page X) <text>` and instructs the model to cite with bracketed numbers. In the rendered answer, every `[N]` token is a clickable link that expands the **View sources** panel and scrolls to the matching source card; the card itself shows the document filename, chunk index, page badge, and character offsets when present.

<Callout type="info">
The admin UI uses session cookies exclusively. To automate anything the admin UI does, mint an API key at `/api-keys` and use it with one of the [SDKs](/docs/sdks/typescript) — or with raw HTTP using the same REST endpoints.
</Callout>

## When to skip the Admin UI

- **Pure backend deployment** — no admin UI process, everything via API keys and SDKs. Set `BIGRAG_ENV=prod` and use [`POST /v1/auth/setup`](/docs/api-reference/authentication) from an admin workstation to bootstrap.
- **Embedded experiences** — if you're surfacing search inside your own app, skip admin UI and build against the [query API](/docs/api-reference/query).
- **Read-only operators** — create a `member` account; they get `/overview`, `/collections` (read), and `/chat` but can't mutate.
