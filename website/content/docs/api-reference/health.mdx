## Health

<Accordions type="multiple">
<Accordion title="GET /health — Liveness check">

No authentication required. Returns `200` if the server is running.

```json
{ "status": "ok", "version": "2026.x.y" }
```

</Accordion>

<Accordion title="GET /health/ready — Readiness check">

No authentication required. Tests connectivity to Postgres, Turbopuffer, Redis, and the configured embedding provider.

**Response** `200` (healthy):

```json
{
  "status": "ok",
  "version": "2026.x.y",
  "postgres": true,
  "vector_store": true,
  "redis": true,
  "embedding": true,
  "embedding_source": "settings"
}
```

**Response** `503` (degraded):

```json
{
  "status": "degraded",
  "version": "2026.x.y",
  "postgres": true,
  "vector_store": true,
  "redis": false,
  "redis_error": "unreachable",
  "embedding": false,
  "embedding_error": "auth_failed",
  "embedding_source": "settings"
}
```

Returns HTTP `503` with `"status": "degraded"` when any dependency is unhealthy. Dependency errors are category labels only: `auth_failed`, `rate_limited`, `timeout`, `unreachable`, `misconfigured`, or `unknown`. The embedding health check result is cached for 60 seconds.

</Accordion>
</Accordions>

## Stats & models

<Accordions type="multiple">
<Accordion title="GET /v1/stats — Platform stats">

Platform-wide statistics including collections, documents, and queue status. This endpoint is not cached.

**Response** `200`:

```json
{
  "status": "degraded",
  "collections": 5,
  "documents": {
    "total": 128,
    "ready": 120,
    "pending": 3,
    "processing": 2,
    "failed": 3,
    "total_chunks": 4850,
    "total_tokens": 285000,
    "total_size_bytes": 524288000
  },
  "webhooks": 2,
  "queue": {
    "queued": 150,
    "completed": 120,
    "failed": 5,
    "pending": 3,
    "processing": 2,
    "retrying": 1,
    "dead_lettered": 2,
    "leased_processing": 2,
    "stale_processing": 0
  },
  "queue_health": {
    "status": "degraded",
    "reasons": ["dead_lettered_jobs", "retrying_jobs"]
  },
  "workers": {
    "online": true,
    "status": "online",
    "heartbeat_at": "2026-05-15T12:00:00+00:00",
    "heartbeat_age_seconds": 4
  }
}
```

`status` summarizes the queue and worker state:

| Value | Meaning |
|-------|---------|
| `ok` | No queue risk detected |
| `degraded` | Worker or queue needs attention but is not blocked |
| `down` | Queued or processing work exists while the worker heartbeat is offline |

`queue_health.reasons` can include: `worker_offline`, `worker_offline_with_active_queue`, `dead_lettered_jobs`, `stale_processing_jobs`, `retrying_jobs`.

When stats detect expired or unrefreshed processing leases, the worker marks those documents pending again and requeues them through the active ingestion queue instead of leaving them as permanently processing.

</Accordion>

## Error codes

All API errors return a JSON body with a `detail` field:

```json
{ "detail": "Error description" }
```

| HTTP Status | Meaning | Common Causes |
|-------------|---------|---------------|
| `400` | Bad Request | Invalid input, missing required fields |
| `401` | Unauthorized | Missing or invalid authentication token |
| `403` | Forbidden | Insufficient permissions |
| `404` | Not Found | Resource doesn't exist |
| `409` | Conflict | Duplicate name |
| `413` | Payload Too Large | File exceeds `BIGRAG_MAX_UPLOAD_SIZE_MB` |
| `500` | Internal Server Error | Server-side error |

<Callout type="info">
Every HTTP response includes an `X-Request-ID` header. Send your own value to correlate client logs with API logs, or let bigRAG generate one.
</Callout>
